## US-005: Fix Activity Timeline in Report (Completed)
**Date**: 2026-01-23

### Changes Made

1. **Fixed UTC timezone issue** (models.js):
   - Added new helper function `formatDateToLocalString(date)` that formats dates using local timezone instead of UTC
   - Updated `getTodayDateString()` to use `formatDateToLocalString()` instead of `toISOString().split('T')[0]`
   - Updated `getDateStringDaysAgo()` to use `formatDateToLocalString()` instead of `toISOString()`
   - Updated `getWeekStartDateString()` to use `formatDateToLocalString()`
   - Updated `getMonthStartDateString()` to use `formatDateToLocalString()`
   - Updated `getDateFromTimestamp()` to use `formatDateToLocalString()`
   - Updated `getActivityByHourForDateRange()` loop to use `formatDateToLocalString()` and parse dates with 'T12:00:00' to avoid edge cases

2. **Fixed weekly chart data calculation** (reportsCharts.js):
   - Changed `calculateWeeklyChartData()` to use `getDateStringDaysAgo()` instead of inline `toISOString()` for consistent local timezone handling
   - Date parsing now uses 'T12:00:00' suffix to avoid timezone edge cases when creating Date objects from date strings

3. **Changed Y-axis day labels to 2-letter uppercase** (reportsCharts.js):
   - Updated `dayNames` array from `['Sun', 'Mon', 'Tue', 'Wed', 'Thu', 'Fri', 'Sat']` to `['SU', 'MO', 'TU', 'WE', 'TH', 'FR', 'SA']`
   - Fixed date parsing in heatmap tooltip to use 'T12:00:00' for consistent behavior

4. **Made activity chart nearly full width** (popup.css):
   - Reduced `.activity-heatmap` padding from `var(--spacing-md)` to `var(--spacing-sm) var(--spacing-xs)`
   - Reduced `.heatmap-hour-labels` margin-left from `40px` to `28px` (to match narrower day labels)
   - Reduced `.heatmap-day-labels` width from `36px` to `24px` (2-letter labels need less space)
   - Reduced `.heatmap-day-label` padding-right from `var(--spacing-xs)` to `4px`

### Key Learnings
- `toISOString()` returns UTC time which causes issues near midnight in local time (e.g., at 1 AM local, UTC date might still be the previous day)
- Always use local date formatting when displaying/comparing dates for user-facing features
- When parsing date strings like '2026-01-23' with `new Date()`, add 'T12:00:00' to avoid timezone edge cases that can shift the date
- For 2-letter day abbreviations, reduce the width of label containers to maximize chart space

## US-020: Fix X-Axis Clipping in Goal Statistics (Completed)
**Date**: 2026-01-23

### Changes Made

1. **Refactored label rendering to use absolute positioning** (statisticsChart.js:105-116):
   - Changed from rendering 30 labels (23 hidden) to only rendering 7 visible labels
   - Labels now use absolute positioning with calculated percentage-based `left` values
   - Position formula: `((index + 0.5) / 30) * 100%` centers labels under their corresponding bars
   - Removed `hidden` class approach in favor of only rendering needed labels

2. **Updated CSS for absolute positioned labels** (popup.css:7821-7833):
   - Changed `.progress-chart-labels` from flexbox to `position: relative` with fixed `height: 16px`
   - Changed `.progress-chart-label` from `flex: 1` to `position: absolute` with `transform: translateX(-50%)` for centering
   - Increased font size from `9px` to `10px` for better readability
   - Removed `min-width: 0`, `overflow: hidden`, `text-overflow: ellipsis` properties that were causing clipping
   - Removed `.progress-chart-label.hidden` rule (no longer needed)

### Root Cause Analysis
The previous implementation had these issues:
- All 30 labels were rendered with `flex: 1`, equally dividing container width
- Hidden labels used `visibility: hidden` which kept them in the layout
- With 30 items sharing space + 2px gaps, each label had very limited width
- Edge labels (index 0, 29) were particularly prone to clipping at container edges
- 2-digit dates (like 25, 29) needed more space than available

### Solution Approach
- Only render the 7 visible labels (indices 0, 5, 10, 15, 20, 25, 29)
- Use absolute positioning to place each label at its exact position
- `transform: translateX(-50%)` centers each label under its bar
- Labels are no longer constrained by flex width calculations
- No overflow/clipping issues since each label has natural width

### Key Learnings
- For sparse label displays on charts, absolute positioning is cleaner than hiding flex items
- Using `visibility: hidden` to hide flex items still affects layout calculations
- The formula `((index + 0.5) / 30) * 100%` centers labels under bars in a 30-bar chart
- `transform: translateX(-50%)` is ideal for centering absolutely positioned elements
- Rendering fewer DOM elements (7 vs 30) is also more performant

## US-020: Fix Settings Screen Scroll Reset on Update (Completed)
**Date**: 2026-01-28

### Changes Made

1. **Modified `renderSettingsScreen()` function** (settings.js:93-570):
   - Added code to capture the current scroll position of `.settings-content` before re-rendering
   - Added code to restore the scroll position after re-rendering using `requestAnimationFrame`
   - The scroll position is only restored if it was greater than 0 (i.e., the user had scrolled)

### Root Cause Analysis
The settings screen was re-rendering the entire `screen.innerHTML` whenever a setting was changed (sound toggle, theme toggle, category deletion, etc.). This complete DOM replacement caused the scroll position to reset to 0 because:
- The scrollable `.settings-content` element was destroyed and recreated
- The browser's default behavior is to start at scroll position 0 for new content

### Solution Approach
1. Before calling `screen.innerHTML = ...`, capture the current `scrollTop` value from the `.settings-content` element
2. After the DOM is replaced and all event listeners are attached, restore the scroll position
3. Use `requestAnimationFrame` to ensure the DOM has been fully rendered before setting `scrollTop`
4. Only restore if `scrollTop > 0` to avoid unnecessary operations

### Key Learnings
- When re-rendering a scrollable container by replacing its innerHTML, scroll position is always lost
- Capturing scroll position before innerHTML replacement and restoring after is a reliable pattern
- `requestAnimationFrame` ensures the browser has completed rendering before manipulating scroll position
- This pattern can be applied to any screen that needs to preserve scroll state during re-renders

## US-023: Implement Multi-Way State Synchronization (Completed)
**Date**: 2026-01-28

### Changes Made

1. **Created new stateSync.js module** (src/popup/features/stateSync.js):
   - New module dedicated to handling cross-view state synchronization
   - Implements `chrome.storage.onChanged` listener for the popup
   - Listens for changes to: goals, activeTimers, settings, achievements, xpData, dailyChallenges, pomodoroStates
   - Uses debounced rendering (50ms) to prevent flickering from rapid consecutive updates
   - Includes `markLocalUpdate()` function to track local updates and prevent re-render loops
   - Deep comparison of state changes to avoid unnecessary re-renders

2. **Updated popup.js** (src/popup/popup.js):
   - Added import for `registerStateSyncCallbacks`, `initStateSync`, `markLocalUpdate`
   - Registered state sync callbacks in `registerFeatureModuleCallbacks()`
   - Called `initStateSync()` in `initApp()` to set up the storage listener
   - Exported `markLocalUpdate` for use by other modules when making local updates

3. **Enhanced widget storage listener** (src/content/widget.js:1699-1725):
   - Modified `setupStorageListener()` to update individual goal displays when progress changes
   - When goals update but no goals added/removed, now iterates through changed goals
   - Calls `updateGoalItem()` for each goal where progress or isActive changed
   - This ensures the widget UI reflects changes made from the popup in real-time

### Architecture

**Before (No Sync):**
```
Popup updates goal → Storage changes → Widget listener detects → Only badge/summary updated
Widget updates goal → Storage changes → Popup has NO listener → Popup state is stale
```

**After (Full Sync):**
```
Popup updates goal → Storage changes → Widget listener detects → Individual goal displays updated
Widget updates goal → Storage changes → Popup listener detects → Debounced re-render triggered
```

### Key Implementation Details

1. **Debounced Rendering**: Uses 50ms debounce to batch rapid changes and prevent UI flickering
2. **Local Update Tracking**: `markLocalUpdate()` marks updates from the popup itself to prevent infinite loops

The compact mode filter bar (`.category-filter-bar.compact-mode-bar`) used a static `background-color: var(--surface)` which didn't adapt to the selected color theme. By adding the compact mode bar to the same selector as `.screen-header`, it now receives the same theme-aware gradient background.

## US-034: Fix Target Count Field Layout (Completed)

### Root Cause Analysis

The counter target input (`.counter-target-input`) had a `max-width: 160px` constraint from the US-032 compacting changes. While this was intended to create a compact centered input, it caused the input to appear disconnected from its container - floating in empty space within the form group.

### Solution

Replaced `max-width: 160px` with `width: 100%` to make the counter input fill its container. The `text-align: center` property is retained to keep the numeric input value centered within the full-width field.

### Files Modified
- `src/popup/css/goal-form.css` (removed max-width constraint, added width: 100%)

### Key Learnings
- When designing compact form inputs, `max-width` constraints can cause visual disconnection from container elements
- Centered text (`text-align: center`) on a full-width input achieves a similar visual effect without the floating appearance
- Form inputs should generally fill their containers for consistent visual alignment with labels, hints, and error messages
- The timer target inputs use `width: 100%` and the counter input should follow the same pattern for consistency

### Implementation

1. **Service Worker (service-worker.js:198-235)**:
   - Added `chrome.contextMenus.onShown` listener to check widget visibility before the menu is displayed
   - Uses `chrome.tabs.sendMessage` to query the content script for widget status
   - Updates the `timer-floater` menu item visibility using `chrome.contextMenus.update({ visible: false/true })`
   - Calls `chrome.contextMenus.refresh()` to apply changes to the context menu
   - Gracefully handles cases where content script is unavailable (e.g., chrome:// pages)
   - Renamed menu item from 'Timer Floater' to 'Show Timer Floater' for clarity

2. **Widget Content Script (widget.js:790-798)**:
   - Added handler for `GET_WIDGET_STATUS` message type
   - Returns visibility status based on: enabled state, dismissed state, and container visibility
   - Allows service worker to dynamically hide/show context menu item

### Technical Details

The implementation uses Chrome Extension APIs:
- `chrome.contextMenus.onShown`: Fires when context menu is about to be displayed
- `chrome.contextMenus.update`: Modifies existing menu items (visibility, title, etc.)
- `chrome.contextMenus.refresh`: Forces menu to update with changes
- `chrome.tabs.sendMessage`: Communicates with content script

Widget visibility is determined by checking:
- `widgetState.enabled` - Widget is enabled in settings
- `!widgetState.dismissed` - Widget was not dismissed for this session
- `this.container` exists and doesn't have `hidden` class

- Error handling is important for content script communication (not all pages support it)
- Menu item visibility can be toggled dynamically with the `visible` property
